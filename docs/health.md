# クロールの日次の健全性（#106）

毎朝、前夜のクロールでエラーが出ていないか、品質が落ちていないかを定期ルーティンで確かめるための集計。
全国規模（収集元が数千）でも読む側の負担が増えないよう、集計と異常の判定はクロールのジョブの最後にサーバー側で済ませる。

## 流れ

1. Cron（03:00 JST の全件、12:00 JST の取り直し）の `runCrawlJob` の最後に `writeHealthReport` を呼ぶ
2. その日（JST）の各収集元の**最後の実行**で集計し、`source_health`（収集元 × 日）と `health_reports`（日ごと 1 行）に書く。同じ日を書き直すと置き換える（12:00 の取り直しで直った収集元は異常から外れる）
3. 読む側は `GET /api/health?date=YYYY-MM-DD` / MCP の `get_health` で、要約と**異常のある収集元だけ**を受け取る（最大 200 件。超えたら `anomaliesTruncated: true`）

対象の収集元は、クロールの対象と同じ（approved・有効・`policy_status` が `ng` でない）。

## 異常の種類

| 種類 | 条件 |
| --- | --- |
| `no_run` | その日に実行がなかった（ジョブが途中で止まった・スキップされた） |
| `failed` | その日の最後の実行が failed。`consecutiveFailedDays` に連続日数 |
| `zero_events` | 0 件だった。直近の成功した日は 1 件以上取れていた |
| `date_rate_drop` | 日付取得率が過去の平均から 20pt 以上低下 |
| `extraction_rate_drop` | 抽出成功率が過去の平均から 20pt 以上低下 |

その日の集計自体がなければ `status: "missing"`（Cron か Worker が止まっている可能性）。

## しきい値（`HEALTH_THRESHOLDS`）

| 名前 | 値 | 理由 |
| --- | --- | --- |
| `baselineDays` | 7 | 曜日による掲載の偏り（週末のイベントが多い）を 1 週間でならす |
| `minBaselineDays` | 3 | 追加したばかりの収集元で、1〜2 回の値を平均と呼んで誤検出しないため |
| `rateDrop` | 0.2 | 自治体ページは月替わりで掲載数が揺れる。10pt 程度の揺れでは騒がず、抽出が崩れたとき（多くは半分以下になる）を拾う |

`failed` は 1 日で異常にする。その日の最後の実行で集計するので、03:00 に失敗して 12:00 の取り直しでも失敗した場合（＝同じ日に 2 回続けて失敗）にだけ残る。
failed の日は率の平均に入れない（失敗で率が下がって見えるのを防ぐ）。
