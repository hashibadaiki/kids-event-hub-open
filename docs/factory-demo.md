# デモ: Claude Code のソフトウェアファクトリー（2 本）

審査で短く見せる 2 つの流れ。どちらも「Claude が進め、人間が要所で採否を決める」ところを見せる。仕組みの全体は README「Claude Code をソフトウェアファクトリーとして回す」。

## デモ 1: issue → Claude が PR → 本人がレビューしてマージ（約 2 分）

| # | 誰が | 画面 | 見せたい点 |
| --- | --- | --- | --- |
| 1 | 人 | GitHub で issue に `ready` ラベルを付ける | 着手の可否は人が決める |
| 2 | Claude（定期実行） | issue に「着手します」→ `planner` が計画 → `implementer` がテストを先に書いて（Red）実装 | TDD。コミットのたびに `pre-commit-check` がテストを走らせる |
| 3 | フック | （録画用に）`wrangler deploy` を打たせると `guard-bash` が止める / `Closes #N` なしの PR を `guard-pr` が止める | やってはいけないことは機械的に止まる |
| 4 | Claude | PR 本文: 変更点・テスト結果・迷った点・オーナー作業 | 人が判断しやすい形で渡す |
| 5 | Claude | `/review-pr <番号>` → `reviewer`（実装を見ていない別エージェント）が要件との対応表と指摘 | 作った本人と別の目 |
| 6 | 人 | マージ操作 → `guard-pr` がチェックリスト付きで確認を求める → 人が承認してマージ | **採否は人が握る** |

実例: このリポジトリの PR 一覧（`issue-<番号>` ブランチ、本文に「オーナー作業」「判断に迷った点」）。

## デモ 2: 品質低下 → 改善案 → 承認 → 採用（約 2 分）

前提: #11（採点・生データ・版管理）と #13（ダッシュボード）がマージ済み。ローカル D1 に、日付の取得率が低い収集元が 1 つある状態を用意する。

| # | 誰が | 画面 | 見せたい点 |
| --- | --- | --- | --- |
| 1 | Claude | `/crawl <収集元>` → 品質スコア 0.55（閾値 0.7 未満） | 品質を毎回数字で見ている |
| 2 | Claude | `/improve <収集元>` → `improver` が取りこぼしサンプルから改善案（指示・ヒント・セレクタ） | 原因の仮説つきの改善案 |
| 3 | Claude | `verifier` が保存済みデータで新旧を再抽出・採点 → 0.55 → 0.62（+0.07）、差分サンプル | 本番に出す前に保存データで検証 |
| 4 | Claude | +0.10 未満なので判定 `human` → 前後比較を見せて「採用 / 却下」を聞く | 微妙な改善は自動で入れない |
| 5 | 人 | 差分サンプルを見て「採用」 | **採否は人が握る** |
| 6 | Claude | v2 を active に、`docs/improvement-log.md` に記録 → ダッシュボード（#13）で前後比較 | 却下した案も含めて記録が残る |
