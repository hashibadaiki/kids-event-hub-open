# クロールの日次の健全性（#106）

毎朝、前夜のクロールでエラーが出ていないか、品質が落ちていないかを定期ルーティンで確かめるための集計。
全国規模（収集元が数千）でも読む側の負担が増えないよう、集計と異常の判定はサーバー側で済ませる。

## 流れ

1. crawler の Worker の 06:30 JST の Cron（`HEALTH_CRON`）が、クロールとは別に `writeHealthReport` を呼ぶ
   - クロールのジョブの最後で書かないのは、収集元が増えてジョブが打ち切られたときに集計まで届かず、毎日 `missing` と誤報になるため
2. 各収集元の**直近 26 時間の最後の実行**で集計し、`source_health`（収集元 × 日）と `health_reports`（日ごと 1 行）に書く。同じ日を書き直すと置き換える
   - 暦の日で区切らないのは、取得時刻が 12:00 にずれた収集元（03:00 に失敗して 12:00 に成功した翌日以降、`/add-source` で日中に初回クロールしたものなど）を `no_run` と誤報しないため
3. 毎朝 07:00 のルーティンが `GET /api/health` / MCP の `get_health` で、要約と**異常のある収集元だけ**を受け取る（最大 200 件。超えたら `anomaliesTruncated: true`）

対象の収集元は、クロールの対象と同じ（approved・有効・`policy_status` が `ng` でない）。

## 異常の種類

| 種類 | 条件 |
| --- | --- |
| `no_run` | 直近 26 時間に実行がなかった |
| `failed` | 2 日以上続けて失敗（日付が 1 日ずつ続いているものだけ数える）。`consecutiveFailedDays` に連続日数。1 日だけの失敗は異常にせず、`failedCount` に数える |
| `zero_events` | 0 件だった。直近の比べられる日は 1 件以上取れていた |
| `event_count_drop` | 件数が過去の平均の半分未満 |
| `date_rate_drop` | 日付取得率が過去の平均から 20pt 以上低下 |

その日の集計自体がなければ `status: "missing"`（Cron か Worker が止まっている可能性）。

**新しい PDF がなかった実行**（PDF 一覧に新着がない。`crawl_runs.nothing_new`）は 0 件でも正常なので、件数・率を判定せず、過去の平均にも入れない。
failed の日も平均に入れない。前日の集計と同じ実行（その後に取得されていない）は二重に数えない。

## しきい値（`HEALTH_THRESHOLDS`）

| 名前 | 値 | 理由 |
| --- | --- | --- |
| `runLookbackHours` | 26 | 1 日 1 回の取得（最後の成功から 20 時間で次の Cron の対象）を、取得時刻が 03:00 でも 12:00 でも拾える幅 |
| `baselineDays` | 7 | 曜日による掲載の偏り（週末のイベントが多い）を 1 週間でならす |
| `minBaselineDays` | 3 | 追加したばかりの収集元で、1〜2 回の値を平均と呼んで誤検出しないため |
| `failedDays` | 2 | 相手サイトの一時的な障害で毎日 issue を立てないため（issue の「連続」） |
| `countDropRatio` | 0.5 | 件数は月替わりで揺れる。抽出が崩れたとき（多くは半分以下になる）だけを拾う |
| `rateDrop` | 0.2 | 10pt 程度の揺れでは騒がず、日付の読み取りが崩れたときを拾う |

抽出成功率（抽出件数 / 取得した文書の数）は判定に使わない。文書 1 つから数十件のイベントが出るので率にならず、件数の揺れで誤検出するため。
